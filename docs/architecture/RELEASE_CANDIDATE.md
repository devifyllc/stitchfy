`SolutionBlueprint.deployment?: DeploymentInfo` — deprecated in favor of `SolutionBlueprint.architecture?: CloudArchitectureSection`. Zero producers, still accepted by validation, not removed in RC1. Locked in by `tests/contracts/solution-blueprint-v1.contract.test.ts`. See ADR-002.

## Package Boundaries

Core: deterministic discovery/planning/architecture-generation/validation, offline codebase analysis, the two offline deterministic exporters (`generic-rest-typescript`, `generic-java-replatform`). Optional/future: live integration providers, AI/model runtime, cloud provisioning, observability vendor configuration, credential handling, network clients, source mutation/patch application. No physical package split in RC1. See ADR-001, ADR-003.

## CLI Compatibility

Documented flags stable within the current CLI generation; new flags additive only; removals require migration docs. See `COMPATIBILITY.md` "CLI compatibility policy."

## Serialization Compatibility

Additive-only within schema v1 (new optional fields/sections); enum additions and validation tightening require review; field removal/rename/incompatible type or enum-meaning changes require a new major schema version. See `COMPATIBILITY.md`.

## Determinism Policy

Domain IDs (`REQ-`, `WF-`, `INT-`, ...) are deterministic and safe for referential integrity. Execution/wrapper IDs (`ImplementationArtifact.id`, `HumanApproval.id`, `WorkflowState.projectId`) and all `generatedAt`/`timestamp` fields are legitimately volatile and documented as such — none were changed in RC1 merely to simplify golden-fixture comparison (see `PUBLIC_CONTRACTS.md` "ID semantics").

## Deferred Runtime Tracks

Phase 5.5B (Runtime Integration Providers), Phase 6.5 (AI Agent Runtime), Phase 7C (Cloud/Observability Runtime Providers), Phase 8.5C (Reviewed Source Transformation / Patch Generation) — all explicitly deferred, none implemented in RC1, rationale in ADR-001/ADR-003.

## Known Limitations

See `docs/architecture/KNOWN_TECHNICAL_DEBT.md` in full. Summary: no intentional npm library export surface exists yet (deliberate RC1 scope boundary, not a defect); the original website pipeline has not been physically migrated under `framework/capabilities/website/`'s newer directory convention (deferred, no user-facing effect); only Maven/npm/Java-source codebase analyzers exist (deferred ecosystem coverage).

## Recommended Version / Merge Decision

**Recommended package version: retain `2.1.0`.** No user-facing breaking contract was introduced — RC1 is documentation, small defect fixes (version-drift, stale phase labels, CLI error UX), and regression tests, not new capability. A `2.1.0 → 2.1.1` or `2.2.0` bump is a decision for whoever cuts the actual release, made separately from this report; RC1 does not touch `package.json`'s `version` field.

**Merge recommendation: READY WITH DOCUMENTED CONDITIONS.**
- Ready: all 8 gates pass; the architecture is internally consistent (zero genuine Type/Zod mismatches found across all 8 audited domains); every deferred track has an explicit, documented rationale (ADR-001/003) rather than being silently absent.
- Conditions: (1) a human should review `docs/architecture/decisions/` and confirm the package-boundary/runtime-provider decisions before treating them as final; (2) the "Open" item in `KNOWN_TECHNICAL_DEBT.md` (no intentional npm export surface) should be a deliberate decision point before anyone tries to `npm install stitchfy` as a library; (3) per the task's own explicit instruction, this report does not perform the merge, tag, or publish — that remains a separate, human-approved action.

See `docs/architecture/ROADMAP.md` "Architecture Stabilization / Release Candidate Review" for the historical record of this decision.
