# AI Agents Capability

Status: **fully implemented capability**. It's the fourth capability beyond the website (after Workflow Automation, Integrations, Security & Governance) to go from structured selection through a validated, artifact producing specification. `implemented: true` means Stitchfy generated and validated one or more vendor neutral AI Agent architecture specifications for the currently known business solution. It does **not** mean an LLM was executed, a tool was invoked, an agent was deployed, outputs are accurate, or the agent is safe, compliant, or production ready. No model provider call, tool execution, MCP server, embedding, vector store, or RAG runtime exists anywhere in this module.

## Pipeline

```
DiscoveryResult (incl. AIAgentNeed[] — a dedicated "AI Agent Needs" section)
     ↓ ai-agents.assessor.ts       (structured, explainable selection)
CapabilityAssessment
     ↓ ai-agents.planner.ts        (one AIAgentCandidate per AIAgentNeed — never split without evidence)
AIAgentPlan
     ↓ execute() reads Workflow Automation's and Integrations' sibling output
WorkflowDefinition[], IntegrationDefinition[]
     ↓ generators/ai-agent-definition.generator.ts   (tools, permissions, memory, guardrails, HITL — all evidence-derived)
AIAgentDefinition[]
     ↓ validators/ai-agent-definition.validator.ts   (referential integrity, no invented permission/tool/confidence)
     ↓ generators/ai-agent-artifact.generator.ts     (per-agent + aggregate JSON/Markdown, tool catalog, Mermaid)
ImplementationArtifact[]  →  output/artifacts/ai-agents/
     ↓ Security & Governance (registers after ai-agents) consumes AIAgentDefinition[] — see its own README/ARCHITECTURE.md section
```

## Structure

```
ai-agents/
├── generators/
│   ├── ai-agent-definition.generator.ts   ← AIAgentCandidate → AIAgentDefinition (tools/permissions/memory/guardrails/HITL)
│   └── ai-agent-artifact.generator.ts     ← AIAgentDefinition[] → JSON/Markdown/tool-catalog/Mermaid artifacts
├── validators/
│   └── ai-agent-definition.validator.ts   ← referential integrity, no-invented-permission/tool/confidence, no orphan tools
├── schemas/
│   ├── ai-agents.types.ts
│   └── ai-agents.schema.ts
├── ai-agents.assessor.ts   ← structured, explainable supports()/assess()
├── ai-agents.planner.ts    ← AIAgentPlan (one candidate per AIAgentNeed)

```

The discovery side `AIAgentNeed` model lives in `framework/discovery/ai-agents/` (`ai-agent-need.types.ts`, `ai-agent-needs.extractor.ts`), parallel to how every other discovery entity (`IntegrationNeed`, `DataEntity`, and so on) has its own directory there.

## Key design points

- **A real, explicit signal, never inferred from generic automation language.** `AIAgentNeed` is only ever captured from a dedicated "AI Agent Needs" section (plus aliases: "AI Agent," "AI Assistant," "AI Capabilities," "AI Requirements"). Manual steps, automation candidates, and multi-system processes, which are Workflow Automation's own signals, never leak into AI Agent selection. Verified empirically: all 5 pre-existing non-AI examples (`appointment-business.md`, `invoice-approval.md`, `api-integration.md`, `rest-export-ready.md`, `customer-data-workflow.md`) produce `not-recommended` with no agents.
- **One coherent need becomes one agent, by default and in practice.** No multi-agent splitting logic exists in this phase; a `Planner`, `Executor`, `Reviewer`, or `Supervisor` agent is never invented just because "multi-agent systems are fashionable." Splitting a need into multiple agents would require judgment (distinct actors, conflicting permissions, separate trust boundaries) with no evidenced example to validate against, so it's deferred and documented rather than half built.
- **Vendor neutral model requirements.** `AIModelRequirements.provider` and `.model` stay `undefined` unless the source explicitly names one, never `"GPT-5"`, `"Claude"`, `"Gemini"`, or `"Bedrock"` by default, and the architecture never ranks or recommends a provider.
- **Tools come only from real architecture.** A tool is only ever generated by matching an `AIAgentNeed` task against a real `IntegrationOperation` or `WorkflowStep`, via `sharesSpecificWord()` (a stricter local variant of Phase 3/4's `sharesSignificantWord()`, needed because generic actor words like "customer" or "employee," and a need's own dominant subject word, for example "invoice" in an invoice triage need, would otherwise produce false positive matches against unrelated steps). Invented tools in the style of `calendar.createEvent()` never appear; a capability like "summarize the invoice" that has no matching integration or workflow operation correctly produces zero tools.
- **A tool existing does not imply permission.** `AIAgentPermission` requires independent grant language evidence (the specific task bullet that produced the tool match must itself use "may," "can," or "is permitted to" language). Tool derivation succeeding on its own is not sufficient.
- **Autonomy is never inferred from tools existing.** `"semi-autonomous"` and `"autonomous"` require explicit source authorization; a prohibition that happens to contain the word "autonomously" (as in "may not cancel appointments autonomously") is correctly excluded from consideration rather than misread as a grant. A write or notify tool with no confirmed approval defaults to `"unknown"`, never `"supervised"` by assumption.
- **Human oversight reuses the existing HITL model.** `AIAgentHumanOversight` wraps the same `HumanApprovalRequest`. When a prohibited action bullet's oversight language matches an existing `WorkflowApproval`, the agent references that exact approval object rather than creating a new one. `createApprovalRequest()` gained optional `id` and `timestamp` overrides (task item 18), so a newly created, agent specific approval is still deterministic, with zero change to Phase 3's existing call sites.
- **Memory never defaults to persistent.** `"session"`, `"persistent"`, and `"unknown"` come only from explicit task text; a negated statement (such as "history should not persist after the session") is correctly read as evidence for `"session"`, not misread as asserting persistence.
- **No numeric confidence or risk fabrication.** `AIConfidencePolicy.threshold` and `AIAgentRiskPolicy.maximumAutonomousRisk` stay unset unless the source explicitly states a number or level. Neither of the two worked examples states one, which proves the restraint empirically rather than by assertion alone.
- **Status never requires a model provider.** `AIAgentDefinition.status` reaches `"complete"` based purely on whether operational and governance facts (interaction mode, autonomy, memory, tool approval status) are resolved. An unresolved model or provider choice is tracked as an information gap, never as a reason to withhold `"complete"`.
